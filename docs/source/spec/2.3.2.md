# 変更仕様 Ver.2.3.2

## 目的

[`src/utsuho/maps.py`](/Users/juno/Projects/utsuho/src/utsuho/maps.py) に集約されているマッピング定義を責務ごとに分割し、可読性・保守性・拡張性を改善する。

本対応で実現したいことは以下のとおり。

- 幅変換とかな変換の責務をコード上で明確に分離する。
- 変更箇所を追いやすくし、修正時の見通しを改善する。
- 将来 `romaji.py` などの変換種別を追加しやすい構造にする。

## 非目的

本対応では、以下は行わない。

- 変換仕様の変更。
- 変換結果の変更。
- 変換アルゴリズムの変更。
- 派生マップ生成ロジックの関数化。
- JSON/YAML など外部データファイルへの移行。
- 性能最適化を主目的とした全面再設計。
- CLI のオプション追加。
- MCP の I/O 変更。
- 公開クラス名や公開関数名の変更。

## 現状

現行の `maps.py` には、以下が 1 ファイルにまとめて定義されている。

- 半角・全角変換用マップ。
- ひらがな・カタカナ変換用マップ。
- 逆引き用の派生マップ。
- 型エイリアス。

利用側では主に [`src/utsuho/converters.py`](/Users/juno/Projects/utsuho/src/utsuho/converters.py) がこれらの定義を `import` している。

## 課題

現状の構成には、以下の課題がある。

- 責務が広く、変更対象を追いにくい。
- 幅変換とかな変換の境界が見えにくい。
- 派生マップの定義位置が増えるほど見通しが悪くなる。
- 新しい変換種別を追加するたびに `maps.py` が肥大化する。

## 方針

### 分割方針

`maps.py` の責務を `mappings` パッケージへ分割する。

想定構成は以下とする。

- `src/utsuho/mappings/__init__.py`。
- `src/utsuho/mappings/common.py`。
- `src/utsuho/mappings/width.py`。
- `src/utsuho/mappings/kana.py`。

将来的にローマ字変換を追加する場合は、同階層に `romaji.py` を追加する。

### モジュール責務

`common.py` には型定義のみを置く。

- `KanaLetterMapping`。
- `SimpleCharacterMap`。

`width.py` には半角・全角変換に関するマップのみを置く。

- `half_to_full_letter_map`。
- `half_to_full_voicing_mark_map`。
- `half_to_full_punctuation_map`。
- `half_to_full_corner_bracket_map`。
- `half_to_full_conjunction_mark_map`。
- `half_to_full_length_mark_map`。
- `half_to_full_space_map`。
- `half_to_full_ascii_symbol_map`。
- `half_to_full_ascii_digit_map`。
- `half_to_full_ascii_alphabet_map`。
- `full_to_half_letter_map`。
- `full_to_half_voicing_mark_map`。
- `full_to_half_punctuation_map`。
- `full_to_half_corner_bracket_map`。
- `full_to_half_conjunction_mark_map`。
- `full_to_half_length_mark_map`。
- `full_to_half_space_map`。
- `full_to_half_ascii_symbol_map`。
- `full_to_half_ascii_digit_map`。
- `full_to_half_ascii_alphabet_map`。
- `full_to_half_wave_dash`。

`kana.py` にはひらがな・カタカナ変換に関するマップのみを置く。

- `hira_to_kana_map`。
- `kana_to_hira_map`。

`mappings/__init__.py` は、利用側の import 窓口として必要な定義を再 export する。

### 定義ルール

`width.py` では、以下の順で定義する。

1. 型 import
2. 半角 → 全角の基底マップ
3. 全角 → 半角の派生マップ
4. 特殊ケースのマップ

`kana.py` では、以下の順で定義する。

1. 型 import
2. `hira_to_kana_map`
3. `kana_to_hira_map`

`full_to_half_*` 系および `kana_to_hira_map` は、現行どおり辞書内包表記でモジュールロード時に構築する。関数化は行わない。

ASCII 数字・英字マップは生成式へ置き換えず、現行どおり直接値を列挙する。

### `maps.py` の扱い

`maps.py` は内部実装であり、互換性維持のために残さない。

理由は以下のとおり。

- 本モジュールは公開 API ではなく内部実装に属する。
- 利用者規模が小さく、内部構成変更の影響は限定的と判断できる。
- 互換レイヤーを残すよりも責務を明確にしたほうが保守性が高い。

したがって、`maps.py` は廃止し、利用側は `mappings` パッケージ経由へ移行する。

### 実装時の確認方針

本対応は構造変更のみであるため、実装時は以下を確認する。

- 既存テストが全通すること。
- 変換結果が変わらないこと。
- import エラーが発生しないこと。

また、参照漏れを防ぐため、`maps` 参照箇所を洗い出してから import を更新する。

## 影響範囲

本対応の影響範囲は以下のとおり。

- `maps.py` を `import` している内部実装。
- マッピング定義の配置。
- `import` パス。

一方で、以下には影響を与えないことを前提とする。

- CLI の外部仕様。
- MCP の外部仕様。
- `utsuho` パッケージの公開コンバータ API。
- 変換結果そのもの。

## 受け入れ条件

以下をすべて満たしたら完了とする。

- `maps.py` の責務が `mappings/common.py`、`mappings/width.py`、`mappings/kana.py` に分割されている。
- 半角・全角変換とかな変換の定義が明確に分離されている。
- `maps.py` が削除されている。
- 利用側 `import` が `mappings` パッケージ経由に整理されている。
- 既存テストがすべて通る。
- 変換結果が一切変わらない。
- CLI / MCP / ライブラリ API の挙動が変わらない。
- 将来 `romaji.py` などを追加しやすい構造になっている。
